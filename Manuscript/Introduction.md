\section{Introduction to the Proposed Work}

Modern software systems are developed and deployed at a pace that makes manual security review increasingly difficult to sustain [1, 11, 15]. Although traditional security tools such as Static Application Security Testing (SAST) and Dynamic Application Security Testing (DAST) are widely used, they often stop at identifying possible weaknesses rather than proving exploitability, generating concrete fixes, and validating that those fixes preserve intended behavior [3, 9, 12, 14]. This creates a practical gap between vulnerability detection and vulnerability remediation. In many real-world workflows, developers must still investigate alerts manually, reproduce attacks, design patches, and rerun tests before a secure fix can be accepted [4, 8, 13].

This project, \textbf{Sentinel}, addresses that gap through an autonomous vulnerability remediation pipeline. Instead of treating security analysis as a reporting task, Sentinel is designed as an end-to-end system that detects vulnerabilities through exploit-driven testing, generates source-code patches using a Large Language Model (LLM), and verifies the resulting fix through structural and behavioral checks [1, 11, 12, 14]. The objective is not only to identify insecure code, but to move directly toward a validated remediation outcome [3, 6, 8, 13].

The architecture of Sentinel integrates several key technologies and system components:
\begin{itemize}
    \item \textbf{Red Agent (Exploit-Driven Detection)}: The first stage of the system focuses on empirical vulnerability confirmation. The Red Agent executes curated payloads against a target application running inside an isolated test harness. Rather than flagging theoretical patterns alone, it records vulnerabilities only when an exploit produces observable insecure behavior. This reduces false positives and grounds later remediation steps in concrete attack evidence [5, 7, 11].
    \item \textbf{Blue Agent (LLM-Based Patch Synthesis)}: Once vulnerabilities are confirmed, the Blue Agent consolidates the vulnerable source code, the successful exploit payloads, and the detected vulnerability classes into a structured prompt. An LLM then generates a candidate patch intended to eliminate the proven weaknesses while preserving legitimate functionality. This enables the system to move beyond diagnosis and into automated code repair [3, 6, 8, 9, 13, 14].
    \item \textbf{Green Agent (Verification and Regression Safety)}: Security remediation is only useful if the proposed patch is both secure and functional. The Green Agent validates candidate fixes through static analysis and dynamic re-testing. It checks whether dangerous constructs remain in the code, reruns the previously successful exploit payloads, and performs normal-use regression checks to confirm that the application still behaves correctly after patching [4, 10, 12, 14].
    \item \textbf{Stateful Multi-Agent Orchestration}: Sentinel uses a stateful workflow architecture to coordinate the Red, Blue, and Green agents. Shared remediation state tracks detected vulnerabilities, successful payloads, patch attempts, iteration counts, and verification outcomes. This allows the system to loop from verification back to patch generation when a fix is incomplete, creating an iterative detect-patch-verify cycle [1, 11, 13, 15].
    \item \textbf{Backend and API Layer}: The backend is implemented with FastAPI and supports long-running remediation workflows, structured state handling, and communication with the frontend dashboard. It also manages logging, workflow execution, and interaction with the LLM and test harness components.
    \item \textbf{Frontend Monitoring Interface}: A React-based frontend provides an operator dashboard for launching workflows and observing live telemetry. It displays vulnerability status, execution logs, patch output, and verification outcomes, making the internal decision process of the pipeline easier to inspect and evaluate.
    \item \textbf{Sandboxed Test Harness}: Since the system intentionally executes adversarial payloads, Sentinel relies on an isolated execution environment for running vulnerable samples safely. This containment layer allows exploit testing and post-patch revalidation to be performed in a controlled setting without exposing the host environment to unnecessary risk [1, 7, 11, 12].
\end{itemize}

Sentinel is evaluated as a proof-of-concept platform for autonomous software security remediation. Its design is motivated by the need for systems that can not only discover vulnerabilities, but also produce actionable and verifiable repairs with minimal manual intervention [1, 3, 12, 15]. By combining adversarial testing, LLM-guided patch generation, and deterministic validation, the project explores a more complete automation model for secure software maintenance [8, 9, 13, 14].

\subsubsection{This paper aims to answer research questions such as}
\begin{itemize}
    \item How can a multi-agent architecture be used to automate the full vulnerability remediation lifecycle, from exploit-based detection to patch verification?
    \item Can LLM-generated patches reliably remediate confirmed software vulnerabilities while preserving intended program behavior?
    \item Does exploit-driven validation reduce false positives and improve the trustworthiness of automated security remediation compared to purely pattern-based approaches?
    \item To what extent can an autonomous detect-patch-verify pipeline improve the speed and practicality of vulnerability handling in software engineering workflows?
\end{itemize}
