\section{Related Work}
\label{sec:Related work}

The development of \textbf{Sentinel} is situated at the intersection of three active research areas: agentic cybersecurity systems, LLM-based automated program repair, and autonomous vulnerability remediation [1, 3, 11, 12, 15]. Prior work in these areas shows strong momentum toward delegating increasingly complex security and software-engineering tasks to coordinated AI systems. However, much of the literature still treats detection, repair, and verification as partially separate problems rather than as a unified end-to-end remediation workflow.

Recent work on \textbf{agentic cybersecurity} has demonstrated that multi-agent architectures can improve adaptability, task decomposition, and operational reasoning in dynamic security environments. Sheth et al. describe agentic AI for autonomous cyber threat hunting and adaptive defense, emphasizing the value of modular intelligent components that can react to evolving attack conditions [1]. Roy similarly presents a multi-agent cybersecurity framework for threat detection and adaptive response [15]. In a more execution-grounded setting, Somma et al. propose an environment-grounded multi-agent workflow for autonomous penetration testing, showing that agent coordination becomes substantially more useful when actions are tied to observable system behavior rather than abstract analysis alone [11]. These works collectively support the design choice behind Sentinel's Red, Blue, and Green agent separation, where offensive testing, repair generation, and verification are assigned specialized roles.

Another important line of related work concerns \textbf{automated red teaming and exploit-oriented evaluation}. AutoRed explores the automation of red-team assessment through strategic reasoning and adaptive attack generation [7], while Zhang et al. present holistic automated red teaming driven by top-down test-case generation and multi-turn interaction [5]. Although these studies focus primarily on discovering weaknesses, they reinforce a key principle adopted in Sentinel: security findings are more trustworthy when supported by active adversarial interaction rather than static suspicion alone. Sentinel extends this principle by using exploit-confirmed evidence not as an endpoint, but as structured input for downstream patch synthesis and verification.

The most directly relevant body of literature is \textbf{LLM-based automated program repair}. Surveys by Anand et al. and Yang et al. document the rapid growth of AI-driven code generation and LLM-based repair methodologies, highlighting the promise of foundation models in bug fixing and patch synthesis [3, 9]. Xia and Zhang show that conversational LLMs can repair a substantial number of real software bugs at low cost [6], while Gu et al. analyze how large language models can be applied effectively to program repair pipelines [8]. Bouzenia et al.'s RepairAgent is particularly relevant because it frames repair as an autonomous agentic process rather than a single isolated model invocation [13]. Xu et al. further study architectural patterns for LLM-based automated patching, helping clarify the design space for repair workflows that combine model inference with supporting execution logic [14]. Together, these studies strongly motivate Sentinel's Blue Agent, which uses grounded vulnerability evidence to synthesize candidate fixes.

Related work also shows that \textbf{alignment and verification} remain central challenges for AI-generated patches. Varzaneh and Riedel discuss the importance of aligning the objective of LLM-based program repair so that generated outputs optimize for true correctness rather than superficial plausibility [4]. Brandt and Zaidman, while focusing on test amplification, underline a complementary idea: automation becomes more useful when paired with mechanisms that preserve developer trust and measurable behavioral validation [10]. These concerns directly inform Sentinel's Green Agent design. Rather than accepting a generated patch purely because it appears reasonable, Sentinel replays successful exploit payloads, performs regression checks on benign behavior, and applies structural analysis before considering a patch valid.

The closest conceptual match to Sentinel is the emerging literature on \textbf{autonomous vulnerability remediation}. Hsieh, Cheng, and Wang describe a zero-touch remediation framework that combines threat intelligence with LLM-enhanced repair generation [12]. This work aligns closely with Sentinel's overall goal of minimizing manual intervention in the remediation loop. However, Sentinel places stronger emphasis on exploit-grounded confirmation and closed-loop verification, making the remediation process explicitly dependent on demonstrated attack success and post-patch adversarial failure. In that sense, Sentinel bridges the gap between cyber-defense agents, repair agents, and automated patching systems by integrating them into a single detect-patch-verify pipeline [11, 12, 13, 14].

\textbf{Drawbacks of existing approaches}

Despite substantial progress, current approaches still exhibit several limitations that motivate the Sentinel architecture. First, many cybersecurity systems remain detection-centric: they identify possible threats or suspicious code patterns but stop short of generating and validating executable fixes [1, 5, 7, 15]. Second, many LLM-based repair methods operate primarily as code-generation tools and do not always ground the repair process in adversarial evidence of exploitability [3, 8, 9, 14]. Third, even when patch generation is automated, the verification stage is often underemphasized, creating the risk of patches that silence a symptom while preserving the underlying weakness or breaking intended functionality [4, 10, 12]. Finally, several agentic systems demonstrate strong task-level capabilities, but fewer studies unify offensive testing, defensive synthesis, and deterministic validation inside a single iterative workflow [11, 13].

Sentinel is designed to address these gaps by combining empirical exploit detection, LLM-assisted patch generation, and post-patch verification within one coordinated system. In this way, the project does not merely adopt ideas from prior work, but synthesizes them into a practical architecture for autonomous vulnerability remediation [1, 3, 11, 12, 14].
